# Start here — qeet-id-server

The Go backend of **Qeet ID**, the identity and access platform every Qeet product signs in with. This
page is a one-page tour for a new engineer. The rules live in [AGENTS.md](../AGENTS.md), and the detail
in [docs/llm/](llm/).

Three words say who holds what:
- an **account** is a person's sign-in;
- an **organization** is a customer;
- an **application** is something that signs people in through Qeet ID.

## The map

One binary (`cmd/api`) holds five bounded contexts, built on a shared platform and wired in one place.

| Folder | What it does | For example |
|---|---|---|
| `internal/access` | How someone proves who they are, and what they may do | `auth` (sign-in, sessions), `passkey`, `mfa`, `recovery`, `authpolicy`, `ipallow`, `threat`, `authorization/{rbac,abac,rebac,authzen}` |
| `internal/identity` | Who exists: organizations, their people and groups | `organization`, `user`, `group`, `invite`, `verification`, `domainverify` |
| `internal/federation` | Signing in through someone else, and others signing in through us | `oidc` (our OAuth/OIDC provider), `saml` (both roles), `oidcsso`, `ldap`, `scim`, `social`, `provision` |
| `internal/developer` | Machine identities and integrations | `apikey`, `principal`, `agent`, `webhook`, `authhook`, `credentials/{secret,tokenvault,vc}` |
| `internal/operations` | Running the business around it | `audit` (reading and verification), `billing`, `entitlements`, `gdpr`, `compliance`, `activity`, `qeetai` |
| `internal/platform` | Shared code that knows no context | `http/httpx`, `http/errs`, `audit` (the writer), `database/postgres`, `crypto/{tokens,envelope,password}`, `config` |
| `internal/bootstrap` | The only place that wires things together | `wire_<context>.go`, `router.go`, `permissions.go` |
| `cmd/` | The binaries | `api`, `scheduler`, `seed` (development demo data) |

Imports follow fixed directions, which lint enforces:
- federation builds on access and identity;
- operations and developer are leaves;
- nothing in a context imports the wiring.

See AGENTS.md rule 3 for the full list.

## One request's path

Every request passes `internal/bootstrap/router.go` in this order:

1. **Request ID and client address** (`httpx.ClientIP`), for logs and audit records.
2. **A path with an encoded `/` or `\` is refused**, so the router and the checks agree on the route.
3. **Security headers, no-store for token responses, tracing, access log, metrics and panic recovery.**
4. **CORS, then CSRF** for browser requests.
5. On authenticated `/v1` routes:
   - **who is calling** (`httpx.RequireAuth`: a bearer token, an API key or a hosted-login session);
   - **the organization scope** (below);
   - **rate limits**;
   - **the route's permission** (`rbac.Enforce` with `RoutePolicies`);
   - **a recent step-up** where the route needs one (`StepUpRoutes`);
   - **idempotency**.
6. **The handler**, in the package's `http.go`. It calls its service, which owns the transaction and
   writes the audit row in it (`internal/platform/audit`).

Errors are declared once, in each package's `errors.go`, as `errs.New(code, kind, message)`. The kind
decides the HTTP status (`httpx.WriteError`).

## Where organization scope is enforced

Organization isolation is the most important rule here. It has four layers:

1. **`httpx.RequireOrganization(r)`** is the only trustworthy source of the caller's organization.
   Never take it from a path, body or header.
2. **`httpx.EnforceOrganizationScope`** refuses a `{organizationID}` path that isn't the caller's.
   `httpx.PathOrganization` repeats that check inside a handler.
3. **Row-level security** (migration `0011`) shows a connection only its organization's rows on the
   organization-administration routes.
4. **`organizationguard`** fails `go test` when a query on an organization-owned table doesn't mention
   `organization_id`.

A person's own routes, background jobs and sign-in run without row-level security. There, a missing
`WHERE organization_id = …` is a real cross-organization leak.

## Package shape

Every domain package looks the same. `internal/developer/agent` is a typical one:

```text
agent.go             package doc, the Service and New (dependencies in, a missing one refused)
http.go              routes and handlers
errors.go            its error codes
lifecycle.go         one file per topic: suspend, resume, decommission
rotate.go            secret rotation
sponsors.go          the people accountable for an agent
queries.sql          its SQL, listed in the root sqlc.yaml
dbgen/               generated by `make sqlc`, never edited by hand
agent_test.go        tests without a database, beside the file they test
agent_db_test.go     tests that need PostgreSQL (//go:build integration)
lifecycle_test.go    …
rotate_db_test.go    …
```

Services get every dependency in their constructor, so a missing one stops the server at start
instead of silently switching a check off.

## Add an endpoint

1. Find the package in [docs/llm/subsystems.md](llm/subsystems.md).
2. Write the handler in its `http.go` and the logic in its service, adding SQL to its `queries.sql`
   and running `make sqlc`.
3. Mount the route in `router.go`, and give it a permission in that context's `wire_<context>.go`.
4. Describe it in `api/openapi/src/` and run `make openapi`: a route without an OpenAPI entry fails
   the tests.
5. Add the tests.

The step-by-step versions of this and other common changes are in [docs/llm/workflows.md](llm/workflows.md).

## Tests

There are two kinds, named after the file they test, in the same folder:

| File | Kind | Needs |
|---|---|---|
| `foo_test.go` | small (unit) | nothing; `go test ./...` |
| `foo_db_test.go` | medium (with a real PostgreSQL 16) | Docker; `make test-db` |

End-to-end browser tests live in the console and hosted-login repositories, not here.

- `go test ./...` runs the small tests and the static guards in seconds.
- `make test-db` runs everything with the race detector against a disposable database.
- `make ci` is the full local gate:
  - build;
  - the database tests;
  - lint (including function length and import directions);
  - the sqlc and OpenAPI drift checks;
  - govulncheck and gosec.

Run it before asking for a review; GitHub CI runs only part of it.
